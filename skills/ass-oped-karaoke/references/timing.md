# `\k` 逐詞時間

卡拉OK特效的品質有一半在時間。最可靠的永遠是耳朵；工具的分工是：

1. **強制對位（`falign.py`）抓初稿**：人聲分離＋已知歌詞的強制對位，決定「哪個字配哪個音」；
2. **`align.py` 微調**：在強制對位的結果附近（±1/4 拍）把詞吸到起音上（`falign.py --refine` 一次做完）；
3. **頻譜目視（`spec.py`）逐句確認**，對不上的改數字。

沒有條件裝強制對位的環境時，第 1 步改成 `align.py --prior spread`，但它粗得多（見下面的實測），
第 3 步的工作量會大很多。工具只能產生初稿，確認過的詞要 pin 住，不然下一次重跑又被改掉。

## 來源行長什麼樣

```
Comment: 0,0:01:40.12,0:01:43.00,OPJP,OP market down,0,0,0,karaoke,{\k0}{\k74}ドル円ショート！　{\k68}ドル円ショート！
```

- 每個詞（或每個字）前面一個 `{\k…}`。半形空白併到前一個音節。
- 不打算真的做逐字變色時，`\k` 只是切段用的，但**不能沒有**
  （見 `pitfalls.md`：沒有 `\k` 的行只有一個長度 0 的音節）。
  這種「只分段、不切軸」的 `\k`，**數值取一幀的毫秒數四捨五入到整數**，也就是 `round(1000/fps)`：

  | fps | `\k` | fps | `\k` |
  | --- | --- | --- | --- |
  | 24000/1001、24 | `\k42` | 30000/1001、30 | `\k33` |
  | 25 | `\k40` | 50 | `\k20` |
  | 60000/1001、60 | `\k17` | 其他 | `round(1000/fps)` |

  所以逐字切段是 `{\k42\-n}字`（24000/1001）或 `{\k33\-n}字`（30000/1001）。
  **整首用同一個值**，換片源幀率時整份跟著換；看到一份檔裡混著 42 和 33，就是有人複製貼上忘了改。
- ED 的全形空白常常要自成一個零長度音節（`{\k0}　`），否則 `noblank` 的判斷和分詞會打架。

讀寫用 API，不要自己寫正規式：

```python
from aegisub_render.ass.karaoke import parse_karaoke_syllables
for syl in parse_karaoke_syllables(line):
    syl.start_time, syl.duration, syl.text
```

`scripts/ktime.py` 就是它的 CLI：

```bash
python -X utf8 scripts/ktime.py extract x.ass                 # 每行每詞的起點（cs，距行首）
python -X utf8 scripts/ktime.py extract x.ass --json t.json   # 存成表，手改數字
python -X utf8 scripts/ktime.py apply   x.ass --json t.json   # 寫回（只動 \k 的長度，不動文字與 inline fx）
python -X utf8 scripts/ktime.py shift   x.ass --line 0:01:40.12 --word 2 +30
```

## 拍點（BPM / B0）

歌詞的詞通常落在 1/4 拍的格點上。先把拍子量出來：

```bash
python -X utf8 scripts/bpm.py ep01.mp4 --start 183.975 --duration 90
# BPM=158.98   first beat 184.010s   ->   B0=184010
```

兩段式：先用頻譜起音的自相關抓粗略 tempo（連同 2×／4× 倍數一起加總，避免抓成半速），
再在它附近做 tempo×相位的細搜尋，讓起音正好落在格線上。回報的「拍點強度」低於平均的 2 倍
就是沒對上，不要硬用。

`B0` 是**本篇時間軸上第一拍的絕對毫秒**，寫進 Lua 當常數；NC 版要跟著平移（見 `variants.md`）。

有了格點之後，用眼睛對：

```bash
python -X utf8 scripts/spec.py ep01.mp4 229.5 234.2 out.png --bpm 158.98 --b0 184.010
```

頻譜圖上方紅色是拍線、下方藍色是 0.1 秒刻度，起音的亮柱對得上哪一條一眼就看得出來。

全混音的圖上伴奏常常把人聲蓋住。加 `--vocal` 只留置中聲像的成分（主唱幾乎都在正中間），
人聲的泛音線和每個音的起點就看得出來；再加 `--ass x.ass --style OPJP` 把檔裡目前的詞起點疊上去
（綠線，數字是行內第幾個詞），對不對一目了然。合聲不在中間，那種句子用 `--vocal side`。

```bash
python -X utf8 scripts/spec.py ep01.mp4 229.5 234.2 out.png --bpm 158.98 --b0 184.010 \
    --vocal --ass x.ass --style OPJP
```

跑過 `falign.py` 之後，快取資料夾裡有一份**分離後的人聲** `vocals_*.wav`（時間軸和影片相同，
`falign.py` 跑完會印出路徑與 `spec.py` 指令）。直接把它當 `spec.py` 的音訊來源，伴奏已經拿掉了，
音符的起點比 `--vocal` 清楚得多（它是單聲道，不需要再加 `--vocal`）：

```bash
python -X utf8 scripts/spec.py .falign-cache/vocals_<…>.wav 229.5 234.2 out.png --bpm 158.98 --b0 184.010 \
    --ass x.ass --style OPJP
```

## 強制對位（初稿）

`scripts/falign.py` 做的事：

1. 從影片切出歌詞那一段（快取在 `.falign-cache`），用 demucs 把人聲從伴奏裡分出來；
2. 歌詞轉成羅馬字（漢字查 `--readings` 的讀音表，和 `align.py` 共用同一份）；
3. torchaudio 的 MMS 強制對位模型在每一行的時間範圍內找每個詞的起點，並給每個詞一個信心值；
4. `--refine --grid B0:BPM`：寫回之後接著跑 `align.py --prior current --sigma 0.25`，
   音訊來源換成分離後的人聲——強制對位已經決定了哪個字配哪個音，對位器只在 ±1/4 拍內把它吸到起音上。

```bash
python -X utf8 scripts/falign.py run x.ass --video ep01.mp4 --style OPJP --readings readings.json   # 只報告
python -X utf8 scripts/falign.py run x.ass --video ep01.mp4 --style OPJP --readings readings.json \
    --write --all --refine --grid 88659:162.96                                                     # 整首寫回＋微調
```

來源行要先切好分詞（每個詞前面一個 `{\k0}` 就夠，時間由它填）。`--write` 要配 `--only <行起點…>` 或 `--all`：`--all` 只在整首都還沒有時間時用，已經有人對過的行
用 `--only` 避開。讀音表裡沒有的漢字會被略過（報告前會列出那些詞），補齊再跑。

### 先問過再裝

它需要另一個 Python 環境（torch 不一定支援 aegisub_render 用的 Python 版本）：`falign.py setup`
用 uv 建在 `~/.cache/ass-oped-karaoke/fa-venv`（約 1 GB，CPU 版 torch），第一次 `run` 再下載
demucs 與 MMS 的模型（合計約 1.3 GB）。環境已經在（`run` 不報「找不到環境」）就直接用；不在的話，
**先問使用者要不要裝**——合計兩 GB 多的下載與磁碟空間，不是可以順手做的事。使用者不想裝，就退回
`align.py --prior spread` ＋頻譜目視，並在回報裡講明時間是走哪一條路抓的。

### 它的限制

- 強制對位把詞放在「某個音的起點」，**不保證那個音就是那個字**。它知道歌詞，不知道旋律，
  也不知道拍子；音節之間沒有清楚的起音時，它只能猜。
- 報告裡前面有 `?` 的詞（信心低於 0.30，或沒對到）當成沒對到；整行信心都低的行整行重對。
- **和聲、半唸半唱、拖長音的句子最容易錯。** 在另一首 132 BPM 的歌上試跑時，四句和聲與兩句短句的
  信心只有 0.03–0.13，幾乎等於沒對到；這種句子直接對著頻譜手對。
- `--refine` 之後 `align.py` 自己的警告（`!`、歌詞相同的行解出不同的節奏）照樣適用。
- demucs 每次分離的結果有一點隨機，重跑時個別詞可能差一格；確認過的詞寫回之後就不要整首重跑。
- **沒有人聽過就要老實說沒聽過。** 上面的實測是「比其他工具好」，不是「可以不用聽」。

### 實測：各種做法差多少

一首 170 BPM 的 OP（只量過這一首；181 個音節起點，和人工抓好的參考時點逐字比對，1/4 拍＝88 ms）：

| 做法 | 中位誤差 | ≤1/4 拍 | 差超過 1 拍 |
| --- | --- | --- | --- |
| `align.py --prior spread` 從零對位 | 330 ms | 13% | 41% |
| 執行者看頻譜人工對格點 | 200 ms | 28% | 27% |
| 自寫起音偵測＋動態規劃（時點對，但配錯字） | 400 ms | 17% | 62% |
| `falign.py`（demucs＋MMS 強制對位） | 60 ms | 57% | 4% |
| `falign.py --refine`（再用 `align.py --prior current --sigma 0.25` 微調） | 50 ms | 61% | 4% |

讀法：先決定「哪個字配哪個音」、再吸到起音上，明顯比從起音反推歌詞好——後兩列的錯大多是
差一兩格，前三列是整個詞配錯音。但即使是最好的一列，也還有四成的詞差超過 1/4 拍，
所以逐句看頻譜這一步省不得。不同的歌（和聲多、伴奏和人聲同頻、唸白多）結果可能差很多；
同一首重跑，個別百分比也會差一兩個點。

## 音訊對位器（微調，或沒有強制對位時的替代）

`scripts/align.py` 做的事：

1. 從影片切出該段立體聲音訊（快取在 `--cache`），只取「置中聲像 × 有音高（HPSS 諧波）」的人聲成分；
2. 證據 ＝ 人聲頻帶的起音強度 ＋ 旋律音高變化（4096 點 chroma 的前後相似度）；
3. 歌詞拆成假名音拍（漢字查 `--readings` 給的讀音表），用 Viterbi 放到 1/4 拍格點上，
   評分 ＝ 證據 ＋ 節奏先驗（詞內偏八分／十六分，詞間可休止）＋ 目前時間的位置先驗（寬鬆）；
   「ー」不需要起音、且它所屬的音節偏好落在 ≥1 拍的長音上，「ん／っ」只弱要求起音；
4. 同一句型重複出現 ≥3 次且在行內位置相同時，先用互相關把各次對齊（並要求小節內位置一致），
   平均證據之後只解一次節奏，再套回每一次——重複樂句的對位因此穩定得多；
5. `--pin` 列出的詞固定不動，其餘詞排在它們之間。

```bash
python -X utf8 scripts/align.py x.ass --video ep01.mp4 --style OPJP \
    --grid 88659:162.96 --report                      # 只報告：每個詞 目前 → 對位結果（以拍為單位）
python -X utf8 scripts/align.py x.ass --video ep01.mp4 --style OPJP \
    --grid 88659:162.96 --write --only 0:22:39.17     # 把指定行的結果寫回 .ass 的 \k
```

`--video` 也可以給分離後的人聲 wav（`falign.py` 產生的 `vocals_*.wav`）；換了音訊來源就要換 `--cache`，
否則會沿用上一次對原混音算好的特徵（`--refine` 會自己處理這件事）。

### 它需要一個「大概的位置」

對位器不是從零聽出每個詞在哪裡，而是在大概的位置附近挑最像起音的格點。這個大概的位置（`--prior`）
從哪來，決定了結果能不能用：

| `--prior` | 大概的位置 | 什麼時候用 |
| --- | --- | --- |
| `current` | 行上現有的 `\k`（±0.6 拍；`--sigma` 可改） | 已經有初稿（強制對位或手抓的），要它幫忙吸到起音上 |
| `spread` | 音拍數在行內等比例分配（±2 拍） | 沒有強制對位可用、歌詞剛切好分詞還沒有任何時間 |
| `auto`（預設） | 一行的詞全擠在同一個起點就 `spread`，否則 `current` | |

強制對位之後的微調用 `current` 配窄的 `--sigma 0.25`（`falign.py --refine` 就是這樣跑的）：
強制對位已經決定了哪個字配哪個音，這裡只該挪一兩格，放寬了反而會把字拉去配隔壁的音。

兩個會把結果毀掉的用法：

- **拿假時間當 `current`**。把每個詞填成平均分配的 `\k` 再跑，結果只會貼著那份平均分配，
  看起來「有跑過」其實等於沒跑。還沒有真的時間就先跑強制對位，沒有強制對位就明講 `--prior spread`。
- **全部填 `\k0` 又強制 `current`**。所有詞的大概位置都在行首，整行會被擠在開頭幾拍。

`spread` 是從起音反推歌詞，結果粗得多（上面的實測：中位誤差 330 ms，只有 13% 的詞在 ±1/4 拍內，
四成差超過 1 拍），所以它只是「先有個東西可以改」，接下來幾乎每一句都要對著頻譜重對。

### 它會自己說哪裡不可信

報告（stderr）會列出三種狀況，遇到就不要採用那幾行：

- 相鄰兩個詞擠在 1/4 拍以內（報告裡詞的前面有 `!`）；
- 歌詞相同的行（副歌的兩次）解出不同的節奏——證據不夠，兩次都不能信；
- `--phrases` 的重複樂句互相對不齊，已退回逐行對位。

沒被標出來的行也不代表對了——警告只抓得到「明顯自相矛盾」的情況。對位器的輸出一律逐句疊在
`spec.py --ass` 的人聲頻譜上看過再採用（分離後的人聲 wav，沒有就 `--vocal`），並在交付時逐句說明
時間的來源（修過／看過沒問題／沒看／推定）。

被標出來的行改成對著人聲頻譜用眼睛對：先把副歌的其中一次對好，同樣的分段時間用 `ktime.py`
套到另一次（行的起點差整數拍），再把確認過的詞 `--pin` 住。

`--phrases` 只把**歌詞相同**的詞當成重複樂句（同一個詞、行內同一個位置、出現 ≥3 次）。

**一定要 `--only`**：不指定行就整首重寫，已經用耳朵確認過的詞也會被動到。
聽起來不對的詞直接改數字（`ktime.py apply`）或在 Aegisub 調，確認過的加進 `--pin`。

漢字讀音表是作品自己的東西（`{"兌換": "だかん", "追証": "おいしょう"}`），放作品資料夾的 JSON，
不要塞進 skill。

## 中文行

中文行不做對位。它的 `\k` 怎麼來，看中文行的特效跟不跟著唱：

- **跟著唱**（中文行和日文行切成同樣的段數，逐詞變化要對上歌聲）：`\k` 從日文行複製過來，
  `ktime.py copy --from OPJP --to OPCHT`。這也是「日中行一一對應」這條規矩的來源。
- **不跟著唱**（整句進退場，或逐字錯開但不對歌聲；中文字數和日文音節對不上是常態）：
  用純切段的 `\k`（每字一個 `{\k42}`，數值見上面的表）。

兩種都可以，重點是和設計一致，而且**中文行不能沒有 `\k`**（沒有 `\k` 的行只有一個長度 0 的音節）。

## 常見錯誤

- **忘記把中文行的 `\k` 一起更新**：lite 版、繁簡版都是另一個檔，改完 `\k` 要複製過去。
  `build.py` 只有給 `--ktiming` 才會改 `\k`，所以日常重建（`build.py x.ass --render`）不會洗掉手調的時間。
- **行的起點被捨到 10ms 之後，行內 `\t` 的相對時間跟著差幾 ms**。時間一律用 `ass_formatted()`。
- **把對位工具的輸出當成定稿**。強制對位與對位器都對起音清楚的日文最準，對長音、氣音、和聲重疊的
  段落會錯；伴奏很滿的副歌，`align.py` 整行都可能不能用（看它自己的警告）。
- **沒聽過卻說對好了**。這個流程裡沒有任何一步能代替耳朵；交出去時要講清楚哪些詞是量出來的、
  哪些是等比例推的、哪幾句最沒把握。
- **換集數時整份重跑對位**。歌詞與逐詞時間不變，換集數只要平移（`macro offset`／`variants.py nc`）。
